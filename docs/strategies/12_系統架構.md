# 系統架構

> 這份文件描述的不是「程式怎麼寫」，是**責任怎麼分配**。
>
> 每一條界線都對應一個決定：誰知道什麼、誰不知道什麼、
> 兩邊怎麼溝通。程式碼是那些決定的結果，不是相反。

---

## 一、四層

```
┌─────────────────────────────────────────────────────────┐
│  前端 / Visualizer                                       │
│  只讀 state.json，只寫 action.json                       │
│  ← 不知道 C++、不知道規則、不知道教練邏輯                 │
└────────────────┬────────────────────────────────────────┘
                 │  檔案系統（JSON）
┌────────────────┴────────────────────────────────────────┐
│  GameManager                                             │
│  回合流程、發牌、序列化、原子寫入                         │
│  ← 不知道 AI 怎麼決策，也不知道提示怎麼產生               │
└────────────────┬────────────────────────────────────────┘
                 │  Player 介面（playTurn）
┌────────────────┴────────────────────────────────────────┐
│  Agent 層                                                │
│  AIAgent_0（對戰型）│ CognitiveCoachAgent（教練型）      │
│  ← 都只透過 Board::applyProposedSets 出牌                │
└────────────────┬────────────────────────────────────────┘
                 │  CoachDomain 介面
┌────────────────┴────────────────────────────────────────┐
│  CoachEngine                                             │
│  什麼時候說、說到多深、掌握度、過關                       │
│  ← 不知道什麼是牌，也不知道什麼是機器人                   │
└─────────────────────────────────────────────────────────┘
```

**每一層都不知道下一層的存在。** 這不是為了好看——
它讓每一層都能被單獨測試，而 614 項測試裡有 31 項就是
在完全沒有真實領域的情況下驗證引擎的。

---

## 二、三條界線與它們的理由

### 界線一：引擎 ↔ 領域

**引擎知道「要不要說」，領域知道「答案是什麼」。**

領域只需回答三件事：

```cpp
std::optional<Move> solve(const State&);              // 現在有沒有解
std::string hint(HintTier, const Move&, const State&); // 翻譯成三種深淺
std::vector<int> classify(const State&, const State&); // 反推用了哪一招
```

**驗證方式：** 實作兩個完全不同的領域——真實的拉密（六招）與
機器人格點導航（BFS 找路）。**引擎一行都沒改。**

| | 拉密 | 格點導航 |
|---|---|---|
| State | 桌面組合 + 手牌 | 機器人位置 + 障礙地圖 |
| Move | 出哪張牌接哪一組 | 往哪個方向走一步 |
| 卡 2 回合說 | 把紅 3 接在第 1 組的頭 | 往「右」走一步 |

**節奏一模一樣，內容完全不同**——前者是引擎的事，後者是領域的事。

> **代價：** 引擎無法針對領域最佳化。例如它不知道
> 「拉密的破冰是一個特殊階段」，所以那個邏輯只能塞進領域的 `solve()`。

---

### 界線二：Agent ↔ GameManager

**Agent 只能透過 `Board::applyProposedSets()` 出牌。**

那個函式做七道檢查，任何一道不過就整批退回：

| 檢查 | 錯誤碼 | 防的是什麼 |
|---|---|---|
| 牌的來源 | `NotPlayerTile` | 用不屬於自己的牌 |
| 重複 | `DuplicateTile` | 同一張牌出現兩次 |
| 桌面完整 | `RemovedOldTile` | 偷偷拿走桌上的牌 |
| 破冰前不動桌面 | `RearrangedDuringMeld` | 還沒證明實力就借用別人的牌 |
| 組合合法 | `InvalidSet` | 出不合規則的組合 |
| 破冰分數 | `MeldTooLow` | 用零星小牌蹭進場 |
| 輪次 | `NotCurrentPlayer` | 不是你的回合 |

**「整批退回」是關鍵。** 部分成立會讓桌面停在一個不確定的中間狀態——
那比直接失敗更糟。

> 測試裡有一組專門驗這件事：送一個必定失敗的提交，
> 然後逐張比對手牌**每一張都還在原位**。

---

### 界線三：C++ ↔ 前端

**兩個 JSON 檔案，方向相反。**

```
C++ →  state.json   →  前端     每回合寫一次
前端 →  action.json  →  C++      使用者作答時寫一次
```

**為什麼用檔案而不是 socket 或 HTTP：**

課程提供的 `server.py` 與 `visualizer/` 已經建立在檔案輪詢上，
沿用同一套機制才不會讓前端需要兩種模式。而且檔案這條路
**除錯時可以直接 `cat`**——這在跨語言溝通時價值很高。

> **代價：** 有輪詢延遲，而且需要處理「讀到寫到一半的檔案」的問題。
> 後者的解法見第四節。

---

## 三、介面契約

### `state.json` — 引擎寫，前端讀

```json
{
  "turn": 12,
  "current_player": "CoachPlayer",
  "game_over": false,
  "winner": null,
  "draw_pile_count": 47,

  "coach_hint": "把 紅色3 接在第 1 組的頭。",
  "recap": null,

  "last_action": {
    "player": "AI_0",
    "kind": "play",
    "ok": true,
    "reason": "Ok"
  },

  "players": [
    {
      "name": "CoachPlayer",
      "hand_count": 9,
      "hand": [
        { "id": 42, "number": 3, "color": "red", "is_joker": false },
        { "id": 88, "number": 0, "color": "none", "is_joker": true }
      ],
      "initial_meld_done": true
    }
  ],

  "board": [
    [ { "id": 12, "number": 4, "color": "red", "is_joker": false } ]
  ]
}
```

**三個欄位值得說明：**

| 欄位 | 為什麼是這個形狀 |
|---|---|
| `coach_hint` | **可為 null。** null 代表「這一回合引擎選擇不說話」——那是設計，不是缺資料。 |
| `recap` | 非 null 時是完整的題目物件，前端顯示並等待作答 |
| `last_action.reason` | 即使 `ok: true` 也有值（"Ok"），讓前端不必分兩種處理 |

**Tile 的四個欄位缺一不可：**

```json
{ "id": 42, "number": 3, "color": "red", "is_joker": false }
```

`id` 看起來多餘（顏色加數字不就決定了嗎？），但**牌堆中每種顏色數字各有兩張**。
沒有 `id` 的話，前端無法區分「這張紅 5」與「那張紅 5」——
而整個引擎的技巧偵測建立在「指標即身分」上。

---

### `action.json` — 前端寫，引擎讀

```json
{ "action": "answer", "choice": 2 }
```

目前只有 recap 作答會用到。引擎讀到之後**立刻刪除該檔案**，
避免同一個動作被處理兩次。

> 逾時的話引擎會放行讓遊戲繼續——**前端當掉不該讓後端卡死。**

---

### `state_history.json` — 整場的歷史

**這是一個陣列，跟 `state.json` 分開存。**

```json
[ { "turn": 1, ... }, { "turn": 2, ... } ]
```

> **這裡有一個踩過的坑。** 早期版本把整場歷史直接覆蓋到 `state.json`，
> 結果 visualizer 讀到陣列而不是物件，畫面直接報錯
> `Cannot read properties of undefined (reading 'first')`。
>
> **根因是兩種不同用途的資料被塞進同一個檔案**——
> 「現在的狀態」與「所有時刻的狀態」在型別上就不相容。
> 分成兩個檔案之後問題消失。

---

## 四、原子寫入

前端是用輪詢讀檔的。如果引擎正在寫、前端正在讀，
前端會拿到半份 JSON——**而半份 JSON 解析失敗，畫面就掛了。**

解法是**先寫暫存檔，再改名**：

```cpp
const std::string tmp = state_file_path + ".tmp";
std::ofstream f(tmp);
f << state_json;
f.close();
std::rename(tmp.c_str(), state_file_path.c_str());   // ← 這一步是原子的
```

`rename()` 在同一個檔案系統內是原子操作——
**前端要嘛讀到舊的完整檔案，要嘛讀到新的完整檔案，不會讀到中間狀態。**

> 這個模式在 `state.json`、`state_history.json`、`clearStateHistory()`
> 三個地方都有用到。

## 五、信箱模式

`CognitiveCoachAgent` 算出提示，但**它沒辦法直接寫進 `state.json`**——
因為 `GameManager` 不知道有教練這回事，而教練也拿不到 GameManager。

解法是一個全域的信箱：

```cpp
// coach_hint_bridge.h
extern std::string g_current_coach_hint;   // Agent 寫，GameManager 讀
extern std::string g_current_recap;
```

**時序很重要：**

```
① Agent 算出提示 → 寫進信箱
② GameManager 匯出 state.json → 讀信箱
③ 前端讀到這一回合的提示
```

`exportState()` 是在 `playTurn()` **之前**執行的，所以提示算出來的當下，
那一輪的 `state.json` 已經包含它了。

> **為什麼用全域變數而不是把兩個類別接起來：**
> 接起來的話 `GameManager` 就要知道 `CognitiveCoachAgent` 的存在，
> 那條界線一破，之後每加一種 Agent 都要改 GameManager。
>
> **代價很明確：** 全域變數不是好設計，多執行緒下會出問題，
> 而且測試時要記得清空。這是一個**知情的取捨**——
> 用一個侷限換一條界線。

---

## 六、資料流：一個回合

```
① GameManager 決定輪到誰
      ↓
② 教練型 Agent：
      CoachDomain::solve()        領域找出解
      CoachEngine::tick()         引擎決定要不要說、說多深
      → g_current_coach_hint      寫進信箱
      ↓
③ GameManager::exportState()
      buildStateJSON()            組出完整狀態
      寫 .tmp → rename            原子寫入
      ↓
④ 前端輪詢讀到新的 state.json，顯示提示
      ↓
⑤ 使用者出牌
      ↓
⑥ Board::applyProposedSets()     七道檢查
      通過 → 落子
      不過 → 整批退回，記錄錯誤碼
      ↓
⑦ CoachEngine::observe()         偵測用了哪一招、更新掌握度
      ↓
⑧ 回到 ①
```

**注意第 ⑦ 步在第 ⑥ 步之後。** 違規的一手不會進到掌握度——
否則玩家可以靠違規的出牌累積過關進度。

---

## 七、這個架構犧牲了什麼

**一、效能。** 每回合寫一次 JSON、前端輪詢一次，
比直接函式呼叫慢好幾個數量級。這對回合制遊戲無所謂，
但如果要做即時的東西就得換掉。

**二、型別安全。** JSON 沒有型別檢查。C++ 這邊改了欄位名，
前端不會編譯失敗，只會在執行時拿到 `undefined`。
**目前只能靠文件（也就是這一份）維持一致。**

**三、全域狀態。** 信箱模式用了全域變數。
它換來的是層與層之間的獨立，但代價是不能多執行緒，
而且測試時要記得清空。

**四、引擎無法針對領域最佳化。** 因為它不知道領域是什麼。

---

## 八、這個架構讓什麼變得可能

**一、換一個領域不用改引擎。**
機器人格點導航接進來的時候，`coach_engine.h` 一行都沒動。

**二、每一層可以單獨測試。**
31 項引擎測試用的是一個假領域，完全不碰拉密。

**三、前端可以獨立開發。**
只要 `state.json` 的格式不變，前端要用什麼技術都行。

**四、對戰型與教練型共用同一套規則引擎。**
兩者都走 `Board::applyProposedSets()`，
所以不可能出現「教練允許但對戰不允許」的情況。
