# 13　關卡局面設計：兩次都做錯的第五關

## 這份文件記錄的是什麼

第五關（大風吹重組）的局面設計，我連續做錯兩次。第一次是功能性的錯誤，第二次是**修好了 bug 卻毀掉設計**——後者比前者值得記。

前十二份文件寫的是「我怎麼做出這個東西」。這一份寫的是「我怎麼把它做壞，兩次」。

---

## 背景：solve() 有隱含的優先序

`RummikubDomain::solve()` 依固定順序嘗試六個 finder：

```cpp
if (!s.initial_meld_done) {
    if (auto m = findInitialMeld(s)) return m;
}
if (auto m = findAttachRun(s))      return m;   // ①
if (auto m = findCompleteGroup(s))  return m;   // ②
if (auto m = findJokerFill(s))      return m;   // ③
if (auto m = findRunSplit(s))       return m;   // ④
if (auto m = findReshuffle(s))      return m;   // ⑤
```

這個順序本身是合理的：先試最簡單的，找不到才動桌面。實際下棋時人也是這樣想的。

**但那表示：只要局面裡存在一個更簡單的解，複雜的招數就永遠不會被找到。**

這件事在寫求解器的時候完全沒問題——玩家要的是「有沒有解」，不是「有沒有某一種特定的解」。

問題出在把同一個 `solve()` 拿來當教學關卡的答案來源。

---

## 第一次做錯：大風吹被接龍搶走

第五關要教「大風吹重組」，我的第一版局面是：

```
桌面  [1] 黑1 黑2 黑3 黑4 黑5 黑6
      [2] 紅9 黃9 藍9
手牌  黑9  黑7
```

設計時我想的是：黑9 補進第二組湊成四色，黑7 接上第一組——**兩個動作合起來就是重組桌面**。

實際跑起來，`solve()` 回傳的是：

```
把 黑色7 接在第 1 組的尾。
```

`findAttachRun` 在 ① 就命中了，④⑤ 根本沒被呼叫。玩家練了三次，三次都在練接龍——**而接龍是第一關教的東西**。

這一關等於不存在。

### 為什麼沒有及早發現

因為 `demo_rummikub.cpp` 印出來的六關提示是**逐招指定**的，不是走 `solve()`：

```cpp
showAllTiers(dom, state5, RT_BOARD_RESHUFFLE);   // 直接指定招數
```

展示程式看起來完全正常，六招的三層提示都印得漂漂亮亮。只有真的坐下來玩，才會發現玩家走的路徑跟展示的路徑不是同一條。

**這就是為什麼需要 `play_campaign.cpp`。** 展示驗證不了它自己。

---

## 修法：讓簡單的路都走不通

第二版的想法是「把接龍和補色都堵死」。

關鍵在於**把手牌的同色鄰居放進「同數字組」而不是「順子」裡**：

```
桌面  [1] 黑5 紅5 藍5      ← 5 的三色組，不是順子
      [2] 黑7 紅7 藍7      ← 7 的三色組
手牌  黑6
```

檢查每一條路：

| finder | 為什麼不成立 |
|---|---|
| `findAttachRun` | 桌上根本沒有順子，接不上 |
| `findCompleteGroup` | 沒有「6 的組」可以補第四色 |
| `findJokerFill` | 手上沒有 Joker |
| `findRunSplit` | 桌上沒有六張以上的順子 |
| `findReshuffle` | **黑5 在 [1]、黑7 在 [2]，鄰居散在兩組 → 命中** |

`findReshuffle` 的觸發條件是「手牌的同色相鄰牌散在不同組合裡」（`adjacent >= 2`）。黑6 的兩個鄰居分屬兩組，剛好滿足。

跑起來確認：

```
Coach（你主動要的）：把桌上黑色的牌拆開重排，就能接上 黑色6。
```

對了。

## 第二次做錯：沒有選擇就沒有判斷

問題是，為了確保沒有更簡單的解，我把手牌砍到只剩一張。

```
手牌  (1)黑6

>
```

玩家看到這個畫面，唯一能做的事就是打 `1`。

不需要看桌面、不需要判斷、不需要理解什麼是重組。**打 `1` 就過關，三次都是。**

引導系統在這一關完全失去意義：Coach 講不講話都無所謂，因為根本沒有卡關的可能。掌握度給出三顆星（自己找到），但那三顆星什麼都沒證明。

### 這個錯誤比第一個嚴重

第一個錯誤是**功能壞掉**——一玩就知道，因為教的招數不對。

第二個錯誤是**功能正常但目的落空**。所有的數字都對：進度累加、三顆星、過關。測試會通過，模擬會通過，只有真的坐在螢幕前面的人會覺得「這在幹嘛」。

**修好了 bug，卻把設計毀掉了。**

---

## 最終版：多張牌，但只有一張對

正確的條件是兩個同時成立：

- 手上要有好幾張，才需要「挑」
- 但只有一張能構成重組，其餘都是死牌（接不上任何東西）

```
桌面  [1] 黑5 紅5 藍5
      [2] 黑7 紅7 藍7
手牌  (1)黃12  (2)黑6  (3)紅2
```

黃12 和紅2 接不上任何東西，只有黑6 能觸發重組。玩家得真的看桌面才知道要打哪一張。

三題的正解位置分別在 `2`、`3`、`1`——**不能靠記位置過關**。

---

## 從這件事得到的三條規則

### 一、關卡局面必須跟 solve() 的優先序一起設計

`solve()` 的優先序是實作細節，但它決定了每個局面的正解是哪一招。設計第 N 關的局面時，必須確認第 1 到 N-1 關的招數在那個局面裡都不成立。

這件事之前沒有寫在任何文件裡，現在寫在這裡。

### 二、「唯一解」和「唯一選項」是兩回事

要教一招，需要的是**這一招是唯一正確的解**，不是**畫面上只有一個按鈕**。

把選項砍到剩一個確實能保證玩家做對，但那是用取消選擇來換取正確率——正確率上升了，學習沒有發生。

### 三、展示、模擬、實玩驗證的是不同的東西

| | 驗證什麼 | 抓不到什麼 |
|---|---|---|
| `demo_rummikub` | 提示文案寫得對不對 | 玩家走的路徑跟展示的路徑不同 |
| `learner_simulation` | 引導門檻的時序合不合理 | 局面本身有沒有教到該教的招 |
| `play_campaign` | 實際玩起來是什麼感覺 | 樣本只有一個人 |

三者互相補不了對方的盲點。第五關的兩個錯誤，前兩者一個都沒抓到。

## 附帶修掉的兩個 bug

在做這一關的時候，另外發現 `play_campaign.cpp` 的 `applyMove()` 有兩處太簡化，導致 `classify()` 認不出動作、進度永遠是 0：

**重組沒有真的拆桌面。** 第一版只是把打出的牌另開一組，桌面原本兩組完好無缺。但 `detectReshuffle` 的判準是「原本某一組不再完整存在」，所以偵測不到。

**長龍切斷的切點差一個索引。** `detectRunSplit` 要求切完之後**每一段都是合法的 Run**。原本切在 `k+1`，讓前半段變成 `[黑1 黑2 黑3 黑4] + 黑4`——重複的牌，不是合法順子。正確的切點是 `k`，前半段「不含」那個數字，打出的牌接上去才成立。

這兩個都屬於「動作看起來做了，但系統認不出來」的類型。**畫面上有回饋，數字卻不動**——那種 bug 特別難從程式碼看出來，只能玩。
