3　關卡局面設計：三次做錯的第五關，和一道沒人走過的接縫

這份文件記錄的是什麼

第五關（大風吹重組）的局面設計，我連續做錯三次。第一次是功能性的錯誤，第二次是修好了 bug 卻毀掉設計，第三次是局面本身在規則上就走不通——而追第三次的時候，翻出了一件比局面更大的事：**整個六關從來沒有人真的走完過，因為過關的最後一道門從頭到尾沒有被打開。**

前十二份文件寫的是「我怎麼做出這個東西」。這一份寫的是「我怎麼把它做壞，三次，而且前兩次的修法讓我更確信自己已經修好了」。

背景：solve() 有隱含的優先序

RummikubDomain::solve() 依固定順序嘗試六個 finder：

```cpp
if (!s.initial_meld_done) {
    if (auto m = findInitialMeld(s)) return m;
}
if (auto m = findAttachRun(s))      return m;   // ①
if (auto m = findCompleteGroup(s))  return m;   // ②
if (auto m = findJokerFill(s))      return m;   // ③
if (auto m = findRunSplit(s))       return m;   // ④
if (auto m = findReshuffle(s))      return m;   // ⑤
```

這個順序本身是合理的：先試最簡單的，找不到才動桌面。實際下棋時人也是這樣想的。

但那表示：只要局面裡存在一個更簡單的解，複雜的招數就永遠不會被找到。

這件事在寫求解器的時候完全沒問題——玩家要的是「有沒有解」，不是「有沒有某一種特定的解」。

問題出在把同一個 solve() 拿來當教學關卡的答案來源。

第一次做錯：大風吹被接龍搶走

第五關要教「大風吹重組」，我的第一版局面是：

```
桌面  [1] 黑1 黑2 黑3 黑4 黑5 黑6
      [2] 紅9 黃9 藍9
手牌  黑9  黑7
```

設計時我想的是：黑9 補進第二組湊成四色，黑7 接上第一組——兩個動作合起來就是重組桌面。

實際跑起來，solve() 回傳的是：

```
把 黑色7 接在第 1 組的尾。
```

findAttachRun 在 ① 就命中了，④⑤ 根本沒被呼叫。玩家練了三次，三次都在練接龍——而接龍是第一關教的東西。

這一關等於不存在。

為什麼沒有及早發現

因為 demo_rummikub.cpp 印出來的六關提示是逐招指定的，不是走 solve()：

```cpp
showAllTiers(dom, state5, RT_BOARD_RESHUFFLE);   // 直接指定招數
```

展示程式看起來完全正常，六招的三層提示都印得漂漂亮亮。只有真的坐下來玩，才會發現玩家走的路徑跟展示的路徑不是同一條。

這就是為什麼需要 play_campaign.cpp。**展示驗證不了它自己。**

修法：讓簡單的路都走不通

第二版的想法是「把接龍和補色都堵死」。

關鍵在於把手牌的同色鄰居放進「同數字組」而不是「順子」裡：

```
桌面  [1] 黑5 紅5 藍5      ← 5 的三色組，不是順子
      [2] 黑7 紅7 藍7      ← 7 的三色組
手牌  黑6
```

檢查每一條路：

| finder | 為什麼不成立 |
|---|---|
| findAttachRun | 桌上根本沒有順子，接不上 |
| findCompleteGroup | 沒有「6 的組」可以補第四色 |
| findJokerFill | 手上沒有 Joker |
| findRunSplit | 桌上沒有六張以上的順子 |
| findReshuffle | 黑5 在 [1]、黑7 在 [2]，鄰居散在兩組 → 命中 |

跑起來確認：

```
Coach（你主動要的）：把桌上黑色的牌拆開重排，就能接上 黑色6。
```

對了。

**但這張表只檢查了「哪一招會被找到」，沒有檢查「那一招做不做得出來」。** 整個第三次失敗就埋在這裡。

第二次做錯：沒有選擇就沒有判斷

問題是，為了確保沒有更簡單的解，我把手牌砍到只剩一張。

```
手牌  (1)黑6

>
```

玩家看到這個畫面，唯一能做的事就是打 1。

不需要看桌面、不需要判斷、不需要理解什麼是重組。打 1 就過關，三次都是。

引導系統在這一關完全失去意義：Coach 講不講話都無所謂，因為根本沒有卡關的可能。掌握度給出三顆星（自己找到），但那三顆星什麼都沒證明。

這個錯誤比第一個嚴重

第一個錯誤是功能壞掉——一玩就知道，因為教的招數不對。

第二個錯誤是功能正常但目的落空。所有的數字都對：進度累加、三顆星、過關。測試會通過，模擬會通過，只有真的坐在螢幕前面的人會覺得「這在幹嘛」。

修好了 bug，卻把設計毀掉了。

第二次的修法：多張牌，但只有一張對

正確的條件是兩個同時成立：

- 手上要有好幾張，才需要「挑」
- 但只有一張能構成重組，其餘都是死牌（接不上任何東西）

```
桌面  [1] 黑5 紅5 藍5
      [2] 黑7 紅7 藍7
手牌  (1)黃12  (2)黑6  (3)紅2
```

黃12 和紅2 接不上任何東西，只有黑6 能觸發重組。玩家得真的看桌面才知道要打哪一張。

三題的正解位置分別在 2、3、1——不能靠記位置過關。

我當時把這一版寫成「最終版」。它不是。

第三次做錯：合法性從頭到尾沒有人檢查

上面那個局面，玩家打下 黑6 之後會發生什麼事？

重組要把 黑5 從 [1] 抽走、黑7 從 [2] 抽走，跟 黑6 拼成 黑5-黑6-黑7。抽完之後：

```
[1] 紅5 藍5      ← 兩張
[2] 紅7 藍7      ← 兩張
```

**三張的 Group 抽掉任何一張就死了。**

所以這個局面不存在合法的重組。findReshuffle 仍然會命中，因為它的觸發條件是「手牌的同色相鄰牌散在不同組合裡（adjacent >= 2）」——那是**圖樣判斷，不是合法性判斷**。黑5 在 [1]、黑7 在 [2]，條件成立，Coach 就開口了。

但玩家照著做，產不出合法的 after 狀態，detectReshuffle 的「原本某一組不再完整存在」永遠達不到合法狀態，classify() 回空，進度永遠是 0。

三個 variant 全部是三張的組。三題都走不通。

修法是一個字的差距：每組補到四張。

```
桌面  [1] 黑5 紅5 藍5 黃5
      [2] 黑7 紅7 藍7 黃7
手牌  (1)黃12  (2)黑6  (3)紅2
```

抽走 黑5 剩 `紅5 藍5 黃5`，合法；抽走 黑7 剩 `紅7 藍7 黃7`，合法；`黑5 黑6 黑7` 合法。三邊都成立。

補第四色之後，前四招仍然都走不通（兩組都已經四色滿了，補不進去），唯一解還是黑6——但現在它真的走得出去。

第三個錯誤為什麼最難發現

第一次：玩起來教的招數不對，一玩就知道。

第二次：玩起來太簡單，坐下來就覺得不對勁。

第三次：**Coach 說的話完全正確，提示指向的也是對的那張牌，玩家照著做了，然後什麼都沒發生。** 畫面上有回饋（「做了：把桌上黑色的牌拆開重排」），數字卻不動。

那一行回饋是從 `domain.hint()` 來的，它只負責把招數翻譯成人話，不保證那一步真的發生了。

然後才發現：根本到不了第五關

追這件事的時候，才注意到一個更前面的問題——我每次測試都是靠 `n` 跳到第五關，而那幾次掌握度表長得一模一樣：

```
接龍頭尾    用出 3　自主 3　***
補第四色    用出 0　自主 0
...
```

第一關有數字，其他全是 0。我一直以為那是因為我跳過去了。

實際上是：**`n` 一次都沒有跳成功過，我從來沒看過第五關。**

接縫在這裡：

```cpp
// coach_session.h
st.moves_done  = engine_.canAdvance();     // 出牌次數與自主次數
st.recap_done  = recap_passed_;            // recap 過了嗎
st.can_advance = st.moves_done && st.recap_done;

bool advance() {
    if (!advanceStatus().can_advance) return false;
    ...
}
```

而 play_campaign.cpp 檢查的是 `advanceStatus().moves_done`——只是其中一個子條件。於是流程變成：

1. 出牌三次 → `moves_done` 為 true → 印「★ 第 1 關過了」
2. 呼叫 `advance()` → 它檢查的是 `can_advance`，recap 沒過，回 false
3. 呼叫端看到 false → 印「六關全部走完」→ break

關卡表還有五關，程式卻結束了。而 `n` 走的也是同一個 `advance()`，所以跳關同樣失敗。

根本原因只有一句：**play_campaign 的介面從來沒有跑過 recap**，`recap_passed_` 永遠是 false。

這不是 bug，是接縫

CoachSession 加上 recap 這一層的時候，coach_session.h 的檔頭就寫得很清楚：

> canAdvance() 只管出牌次數，recapPassed() 另外判斷。
> 分開是為了讓介面能顯示「出牌條件已達成，接下來是 recap」。

設計是對的，而且意圖寫在程式碼裡。問題是：**介面沒有跟上。** play_campaign 還照 CoachEngine 的玩法在用 CoachSession——`engine.canAdvance()` 換成 `session.advanceStatus().moves_done`，看起來是一對一的替換，實際上語意變了。

兩邊都沒壞。coach/test_session.cpp 測 CoachSession，過。play_campaign 自己編得過、跑得動。壞的是中間那條線，而那條線上沒有測試，因為測試是照模組切的。

還有一層更隱蔽的：`advance()` 的回傳值。

```cpp
bool advance() {
    if (!advanceStatus().can_advance) return false;   // 條件不足
    ...
    return engine_.advance();                          // 沒有下一關也是 false
}
```

同一個 false 有兩個意思，呼叫端分不出來。這讓「recap 沒過」長得跟「六關走完了」一模一樣——所以錯誤訊息不但沒幫忙，還主動誤導。

從這件事得到的五條規則

一、關卡局面必須跟 solve() 的優先序一起設計

solve() 的優先序是實作細節，但它決定了每個局面的正解是哪一招。設計第 N 關的局面時，必須確認第 1 到 N-1 關的招數在那個局面裡都不成立。

二、「唯一解」和「唯一選項」是兩回事

要教一招，需要的是這一招是唯一正確的解，不是畫面上只有一個按鈕。

把選項砍到剩一個確實能保證玩家做對，但那是用取消選擇來換取正確率——正確率上升了，學習沒有發生。

三、finder 命中不等於這一步合法

觸發條件是圖樣比對，可執行性是另一回事。每個關卡局面除了要通過「前 N-1 招都不成立」，還要通過「這一招真的能產出合法盤面」。

這一條應該寫成斷言，而不是靠玩：

```
assert(solve(level) 回傳的招數 == 這一關要教的招數);
assert(applyMove(level, 該招) 之後，每一組都通過 isValidSet);
```

第二行就是三次都缺的那一行。

四、核心多一層，介面不會自己跟上

CoachSession 在 CoachEngine 外面加了模式、挑戰、recap 三層。每一層都有自己的測試，每一層都過。但「呼叫端有沒有用對」不在任何一層的測試範圍裡。

把 `canAdvance()` 換成 `advanceStatus().moves_done` 是一次看起來無害的替換，而它讓整個六關變成一關。

五、布林回傳值不要同時代表兩件事

「條件不足」和「沒有下一關」都回 false，呼叫端只能猜。猜錯的代價是印出一個完全相反的訊息。

要嘛回列舉，要嘛讓呼叫端用別的方式判斷邊界（這次的修法是用關卡數）。

四種驗證，各自看不見的東西

| | 驗證什麼 | 抓不到什麼 |
|---|---|---|
| demo_rummikub | 提示文案寫得對不對 | 玩家走的路徑跟展示的路徑不同 |
| learner_simulation | 引導門檻的時序合不合理 | 局面本身有沒有教到該教的招 |
| 模組單元測試 | 每個模組自己的邏輯 | 模組之間的接縫 |
| play_campaign | 實際玩起來是什麼感覺 | 樣本只有一個人 |

四者互相補不了對方的盲點。第五關的三個錯誤，前三者一個都沒抓到。

附帶修掉的三個 bug

**重組沒有真的拆桌面。** 第一版只是把打出的牌另開一組，桌面原本兩組完好無缺。但 detectReshuffle 的判準是「原本某一組不再完整存在」，所以偵測不到。

**長龍切斷的切點差一個索引。** detectRunSplit 要求切完之後每一段都是合法的 Run。原本切在 k+1，讓前半段變成 [黑1 黑2 黑3 黑4] + 黑4——重複的牌，不是合法順子。正確的切點是 k，前半段「不含」那個數字，打出的牌接上去才成立。

**touched_board 的定義在兩支程式裡不一樣。** demo_session.cpp 寫的是看招數：

```cpp
mm.touched_board = (tech == RT_BOARD_RESHUFFLE || tech == RT_RUN_SPLIT);
```

play_campaign 寫的是看出手前桌面有沒有牌：

```cpp
mm.touched_board = !before.board.empty();   // 錯
```

這個值餵給 mini_battle 的 BattleField::TOUCHED_BOARD，所以自訂挑戰的判定會跟著歪。已統一成前者。

這三個都屬於「動作看起來做了，但系統認不出來」的類型。畫面上有回饋，數字卻不動——那種 bug 特別難從程式碼看出來，只能玩。

一句話

前兩次是我把局面設計錯了。

第三次是我**從來沒有檢查過那一步做不做得出來**，而且因為介面的接縫，我連檢查的機會都沒有——程式在第一關就宣布六關走完了。

展示驗證不了它自己；模組的單元測試驗證不了模組之間；而這兩句話加起來的意思是：**沒有人坐下來玩，就不知道這東西能不能玩。**
